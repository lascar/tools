Référence des scripts .sh actuels

Retour au README des outils · Workflow quotidien · Version TXT

Inventaire du 15 octobre 2026 : 30 fichiers `.sh`, dont 28 commandes et 2 fichiers de support Bash. La liste correspond au dossier parent, sans scripts déplacés ni anciennes copies. Les arguments ont été recoupés avec les aides actuelles et les modules appelés.

Les exemples supposent que le dossier des outils est dans le PATH. <tâche> représente un nom tel que 1234_ma_tache ; les tickets suivent la forme t_2345_mon_ticket. Ne recopie pas les chevrons de la syntaxe dans une commande réelle.

La racine principale, les conventions Git et les services viennent du .env. Les noms historiques contenant master restent des noms de commandes ; ils utilisent la branche principale configurée. Les patchs, archives et fichiers .done restent exclusivement dans WT_MAIN_ROOT/doc.

Rejoindre et gérer les ateliers

worktree_reach.sh

worktree_reach.sh [tâche] [--no-update] [--prepare-only] [--mode mode]

Commande habituelle pour rejoindre une tâche. Crée la branche si elle manque, rattache un worktree si nécessaire, ouvre un atelier fermé ou affiche un atelier vivant. Une création part de la base locale ; une ouverture existante suit l’actualisation habituelle, sauf option ou choix contraire. Un atelier vivant est seulement affiché, sans actualisation Git ni activation Docker.

Sans tâche, affiche le terminal principal existant. Le dossier du terminal appelant est conservé. Une fenêtre ou un onglet manquant provoque une erreur ; l’affichage d’un atelier partiellement ouvert ne crée pas un deuxième atelier.

worktree_reach.sh 1234_ma_tache
worktree_reach.sh 1234_ma_tache --no-update
worktree_reach.sh

worktree_new.sh

worktree_new.sh <tâche> [--prepare-only] [--mode mode]

Crée explicitement une nouvelle branche et son worktree depuis la branche principale locale, puis prépare l’atelier. Refuse une branche déjà connue ou une destination occupée. Ne fait pas de fetch. --prepare-only prépare sans fenêtre ni activation Docker et conserve le dossier appelant.

worktree_open.sh

worktree_open.sh <tâche> [--no-update] [--prepare-only] [--mode mode]

Ouvre une branche existante, locale ou déjà connue dans les références distantes. Réutilise son worktree ou le rattache si nécessaire. Sans --no-update, actualise la base distante, met à jour la base locale en avance rapide et fusionne dans la tâche lorsque le choix effectué le prévoit.

Un travail local déclenche le menu de conservation, sauvegarde/nettoyage, élimination ou annulation. Un conflit non résolu ou un échec de préparation empêche l’ouverture. --prepare-only garde les contrôles et l’éventuelle actualisation, sans fenêtre ni Docker.

worktree_open_current.sh

worktree_open_current.sh

Ouvre l’atelier du worktree de tâche courant. Exige d’être dans ce worktree. N’effectue pas l’actualisation Git de worktree_open.sh ; l’ouverture peut proposer les patchs en attente puis activer les services.

worktree_switch.sh

worktree_switch.sh [tâche]

Affiche le terminal principal sans argument, ou l’onglet d’agent d’une tâche déjà ouverte. Utilise la session GNOME existante, sans créer de fenêtre, modifier Git ou activer Docker.

Pour le principal, recherche un shell dont le dossier physique est la racine principale et préfère le plus ancien. Pour une tâche, nécessite un superviseur d’agent vivant.

worktree_status.sh

worktree_status.sh

Affiche les worktrees enregistrés, leurs branches et leurs changements Git suivis ou non suivis. Pour chaque tâche, indique atelier OUVERT avec les onglets actifs ou atelier fermé, puis donne le nombre total d’ateliers ouverts. Un onglet géré encore vivant suffit, même sans Codex ; les anciens états et PID périmés sont ignorés. Les terminaux ouverts manuellement en dehors des outils ne sont pas comptés. Lecture seule ; ne lance pas de service et ne nettoie rien. Pour les états Docker, utilise worktree_docker.sh status.

worktree_close.sh

worktree_close.sh [tâche]

Avec une tâche, ferme uniquement l’atelier nommé. Sans argument depuis un worktree de tâche, ferme cet atelier. Sans argument depuis le dépôt principal, ferme successivement tous les ateliers de worktree ouverts détectés par worktree_status.sh, en conservant le terminal et les services du principal. Les ateliers fermés sont ignorés. Vérifie les buffers et commandes actives, propose si nécessaire l’arrêt coopératif de commandes, arrête les services ciblés puis sauvegarde les changements en patch dans WT_MAIN_ROOT/doc avant la fermeture finale.

Un refus, une commande non arrêtée ou un échec de sauvegarde bloque la suite. Lors d’une fermeture collective, le premier blocage interrompt les fermetures restantes et indique combien ont déjà réussi ; les ateliers déjà fermés le restent. Le worktree, sa branche et son journal central sont conservés. La fonction Bash ramène au principal si le shell reste ouvert ; un terminal supplémentaire de l’atelier peut être fermé.

worktree_remove.sh

worktree_remove.sh <tâche>

À lancer depuis le dépôt principal, hors du dossier à retirer, après décision explicite de suppression. Vérifie l’identité du worktree, l’absence d’activité et les changements Git, puis crée et relit une archive des fichiers locaux, y compris ignorés. Retire ensuite le worktree et son dossier.

Conserve la branche et le journal central. Ne supprime aucune branche distante. Refuse une cible ambiguë, verrouillée, active ou modifiée. Un retrait partiel ou un problème de permissions peut nécessiter une intervention privilégiée ciblée, après sauvegarde vérifiée.

change_branch.sh

change_branch.sh <tâche>

Fonction Bash à charger avec worktree_shell.sh. Vise une branche déjà rattachée à un worktree, sans créer de branche ni de worktree.

Contrôle la propreté du départ, du principal et de la cible ; refuse l’activité détectée dans la cible ; actualise la branche principale par pull en avance rapide ; déplace le terminal dans la tâche puis y fusionne la base. Le principal doit déjà être sur sa branche principale. Aucun atelier ni serveur n’est lancé.

Pour un processus de ton utilisateur dont le répertoire courant est protégé, la vérification utilise sudo readlink uniquement sur /proc/<PID>/cwd et peut demander ton mot de passe. Un processus extérieur au worktree ne bloque pas la commande ; une activité dans le worktree ou une vérification impossible reste bloquante.

Un refus préalable garde le dossier initial. Un conflit laisse le terminal dans la tâche. L’exécutable seul indique comment charger la fonction ; --help reste disponible directement.

Sauvegardes et rapports

patch.sh

patch.sh
patch.sh make [--include chemin]
patch.sh <tâche> [--include chemin]
patch.sh list
patch.sh restore doc/<patch> [--yes]

Sans argument, propose les sauvegardes en attente de la tâche courante et demande confirmation avant restauration. Sans terminal interactif, affiche les propositions sans les appliquer. L’absence de sauvegarde est signalée.

make sauvegarde le worktree courant. Un nom de tâche sauvegarde son worktree existant depuis un autre dossier du projet. Les archives sont uniques, vérifiées et stockées dans WT_MAIN_ROOT/doc. Elles comprennent l’index, les changements suivis, suppressions, binaires et fichiers nouveaux non ignorés. --include ajoute explicitement un chemin local normalement exclu ; à réserver aux fichiers que tu souhaites réellement sauvegarder.

list affiche les sauvegardes en attente de la tâche courante. restore vérifie l’archive, la branche, le commit de base, les collisions et l’état local. Les fichiers non suivis déjà présents sont compatibles seulement s’ils correspondent strictement au manifeste. Un autre changement bloque la restauration. La vérification est répétée sous verrou.

Après restauration vérifiée, le fichier est renommé .done dans le dossier central. doc/<patch> est résolu vers ce dossier, même depuis un worktree ; un chemin absolu extérieur est refusé. Aucun merge automatique. --yes exige une archive désignée avec restore ; il ne s’applique pas à la forme sans argument.

patch.sh make
patch.sh
patch.sh restore doc/NOM_DU_PATCH.wtpatch.zip

is_any_patch.sh

is_any_patch.sh [tâche] [done]

Liste les sauvegardes de la tâche nommée dans WT_MAIN_ROOT/doc. Aucune branche ni aucun worktree n’est nécessaire pour une tâche explicite. Sans tâche, utilise le worktree courant. Sans done, liste les sauvegardes en attente ; avec done, liste celles déjà traitées. La forme historique is_any_patch.sh done reste valide.

Aucun patch appliqué, déplacé ou renommé. Une liste vide signifie qu’aucune sauvegarde de cet état n’a été trouvée.

is_any_patch.sh 1234_ma_tache
is_any_patch.sh 1234_ma_tache done
is_any_patch.sh done

desc_git.sh

desc_git.sh [tâche]

Décrit la tâche nommée, dont le worktree doit exister ; sans argument, utilise le worktree courant. Écrit <tâche>_git.txt dans le dossier de documentation central WT_MAIN_ROOT/WT_DOCUMENTS_DIR, y compris depuis un worktree.

Le rapport commence par les fichiers modifiés, triés et dédoublonnés, puis détaille les commits accessibles depuis HEAD dont le sujet commence par le nom exact de tâche suivi d’un espace, de deux-points ou de la fin du sujet. Il inclut les commits déjà intégrés dans la branche principale, les suppressions et les anciens/nouveaux chemins de renommage. Les fusions utilisent les différences combinées pour limiter les fichiers importés.

Ne remplace pas les notes de la tâche. Ne décrit pas les modifications locales non committées. Aucun checkout, fetch ou merge.

worktree_check_conflicts.sh

worktree_check_conflicts.sh [chemins...] [--against référence]

Cherche les modifications des mêmes chemins dans les autres worktrees, en tenant compte de l’index, des changements non indexés et des fichiers non suivis. Sans chemin, examine les fichiers actuellement changés.

--against ajoute une simulation Git de fusion avec la référence indiquée, sans appliquer le résultat aux fichiers ni changer de branche. Peut créer des objets internes de simulation dans Git. Un code de sortie non nul peut signaler une collision ou un conflit simulé. L’absence de collision locale ne garantit pas une future fusion sans conflit.

Services et tests

worktree_lance_master.sh

worktree_lance_master.sh [--mode mode]

Depuis le terminal GNOME du dépôt principal sur la branche principale configurée, active ses services et ajoute les onglets de console et de serveur dans cette même fenêtre. Le dossier appelant reste disponible. Les libellés et services viennent du profil.

Sans mode explicite, conserve le mode existant, sinon utilise le mode prévu par l’implémentation. Chaque appel ouvre de nouveaux onglets. Ctrl-P puis Ctrl-Q détache un service sans l’arrêter.

worktree_docker.sh

worktree_docker.sh <action> [--worktree chemin] [--mode mode] [--infrastructure]

Actions actuelles :

  • status : afficher les états et montages des runtimes ; l’URL n’est affichée que pour un runtime actif.
  • activate : configurer et démarrer le runtime ciblé, avec ses montages, ports et volumes propres.
  • stop : arrêter ses services ; --infrastructure demande aussi l’arrêt des services communs et est refusé si un autre worktree les utilise.
  • console : attacher la console de la cible.
  • attach : attacher le serveur du mode actif.
  • shell : ouvrir un shell applicatif dans un conteneur temporaire du runtime.
  • logs : suivre les logs du serveur.
  • restart : redémarrer le service serveur ciblé.

Sans --worktree, utilise le contexte courant. Les actions interactives exigent un runtime actif. L’infrastructure commune et les ports sont pilotés par le .env ; changer les paramètres d’identité de conteneurs existants demande une migration comprise.

worktree_docker.sh status
worktree_docker.sh activate --mode http
worktree_docker.sh logs

relance_serveur.sh

relance_serveur.sh [tâche] [--mode mode]

Remet en service le serveur courant ou celui d’une tâche existante, après vérification de l’infrastructure. Réutilise l’onglet géré lorsqu’il est disponible ; sinon, attache le service dans le terminal appelant. Ne redémarre pas les autres ateliers.

relance_console.sh

relance_console.sh [tâche] [--mode mode]

Même ciblage que la relance serveur, pour le rôle console. Réutilise l’onglet géré ou attache dans le terminal appelant. La console et son service sont ceux configurés pour le projet.

relance_docker.sh

relance_docker.sh [tâche] [--mode mode]

Dans le code actuel, suit le même chemin de relance que relance_serveur.sh. Ce nom ne signifie pas un redémarrage du démon Docker ni un arrêt global des conteneurs.

docker_stop_all.sh

docker_stop_all.sh [--infrastructure]

Le périmètre dépend du contexte. Depuis une tâche, arrête son runtime ; l’arrêt de l’infrastructure commune reste soumis aux protections des autres worktrees.

Sur la branche principale, arrête les conteneurs reconnus du projet principal, de la CI et des runtimes worktree, puis marque leurs états arrêtés. C’est une action globale sur le projet : les services des autres tâches sont concernés. Ne ferme pas leurs fenêtres ni leurs fichiers.

worktree_test.sh

worktree_test.sh <arguments du runner>

Exige un worktree de tâche. Lance la commande CI configurée avec le code de cette tâche, ses montages et un cache séparé. Les exécutions sont sérialisées par un verrou commun.

L’implémentation actuelle accepte --db-setup et --no-db-setup, ajoute la seconde option si aucune n’est fournie, refuse leur combinaison et contrôle l’empreinte du schéma de test. --db-setup peut réinitialiser la base de test : utilise-le explicitement pour cette intention. Les scopes et chemins valides dépendent du runner configuré.

worktree_test.sh file chemin/du_test --no-db-setup

Git et sessions

pull.sh

pull.sh

Exécute uniquement git pull --ff-only dans le dossier courant. Ne sélectionne ni branche ni dépôt à ta place. Refuse les arguments supplémentaires ; --help affiche l’usage.

commit.sh

commit.sh <message> [--no-verify]

À lancer dans le worktree de tâche après préparation explicite de l’index. Vérifie les conflits, les fichiers personnels et les erreurs de diff, puis crée le commit avec le préfixe automatique <nom de tâche> :.

Les messages ordinaires suivent Conventional Commits, par exemple fix: corriger le comportement. Ne fournis pas le nom de tâche. Les messages spéciaux définis dans WT_SPECIAL_COMMITS peuvent ajouter leurs fichiers configurés avant le commit ; les protections des fichiers personnels restent vérifiées ensuite. --no-verify désactive les hooks Git uniquement sur choix explicite.

commit.sh 'fix: corriger le comportement'

push.sh

push.sh [destination] [--force-with-lease]

Pousse la branche du worktree de tâche vers la destination configurée, par défaut le remote principal. Ne pousse pas la branche principale. Une destination peut prévoir une commande préalable, définie dans le .env.

--force-with-lease est limité aux remotes explicitement autorisés ; le SHA distant attendu est relu avant le push. Le script ne fait pas de commit ni de fusion.

merge_to_master.sh

merge_to_master.sh [jours] [auteur] [cible] [--fetch | --no-fetch]

Audit des commits de l’auteur durant la période, sept jours par défaut, et de leur intégration dans la cible principale. Sans auteur, utilise l’e-mail Git configuré. Signale aussi les commits des branches locales absents des références distantes connues.

Actualise les références par fetch et prune par défaut. --no-fetch évite cet accès et utilise les références locales. Malgré son nom, ne réalise aucune fusion, aucun push ni déploiement.

merge_to_dev.sh

merge_to_dev.sh [jours] [auteur] [cible] [--fetch | --no-fetch]

Même audit que merge_to_master.sh, avec une cible de développement explicite ou choisie parmi les références définies dans WT_AUDIT_TARGETS. Si aucune cible n’est trouvée, demande une référence explicite. Ne fusionne rien.

relance_codex.sh

relance_codex.sh [--new-session] [-- arguments de l’agent]

Prépare le contexte personnel du worktree courant et reprend la session d’agent associée quand un lien central valide existe. --new-session démarre une nouvelle session. Les journaux restent dans le dossier central configuré ; les transcriptions natives ne sont pas réécrites.

Le dossier de travail est fixé au worktree : les options d’agent qui changeraient ce dossier sont refusées. Une reprise ambiguë ou un lien cassé demande une vérification explicite.

vim_session.sh

vim_session.sh [doc]

Sans argument, ouvre la session d’éditeur de développement existante. Avec doc, ouvre la session de documentation ; à défaut de session mais avec des notes, ouvre directement celles de la tâche. Si rien n’est disponible, le signale.

Cette ouverture autonome n’est pas un onglet supervisé par la fermeture de l’atelier. Dans un atelier, l’onglet documentation utilise les mêmes sessions et les contrôles de fermeture des buffers ; l’onglet Bash reste un Bash.

put_branch_in_idea.sh

put_branch_in_idea.sh

Écrit le nom de la branche courante dans le fichier marqueur configuré, .idea par défaut. Refuse d’écraser un répertoire IDE existant. Ne change pas de branche et ne configure pas l’IDE.

Fichiers de support Bash

worktree_shell.sh

source /chemin/vers/tools/worktree_shell.sh

Définit les fonctions worktree_reach.sh, worktree_open.sh, worktree_new.sh, worktree_close.sh et change_branch.sh dans le terminal appelant.

Les fonctions d’ouverture conservent le dossier de départ. change_branch.sh permet le vrai déplacement du shell dans la tâche. La fonction de fermeture revient au principal lorsque le shell est conservé. Recharge ce fichier après une modification de ces fonctions ; ce n’est pas une commande à exécuter pour ouvrir un atelier.

worktree_bashrc.sh

Fichier chargé automatiquement par les shells des onglets gérés. Charge la configuration Bash personnelle et installe le mécanisme de fermeture coopérative. Un shell contenant des jobs actifs ou suspendus ne se ferme pas automatiquement.

Lit les variables de fermeture WT_* et, si nécessaire, les préfixes historiques autorisés dans la configuration. Ne le lance pas directement pour rejoindre une tâche ; utilise les commandes d’ouverture ou le fichier de fonctions.
